# 테스트 코드

### 핵심 원칙

- **행동을 검증하고 구현을 검증하지 않기**: private 메서드나 내부 호출 횟수보다, 입력 대비 결과와 부작용을 봅니다.
- **항상 결정적이어야 함**: 시간, 랜덤, 네트워크, 외부 상태 때문에 가끔 깨지는 테스트는 거의 독입니다.
- **빠르고 독립적이어야 함**: 테스트 하나가 다른 테스트의 순서나 데이터에 의존하면 운영에서 금방 문제 납니다.
- **실패 메시지가 바로 이해돼야 함**: 깨졌을 때 “무엇이 왜 문제인지” 바로 보여야 합니다.
- **프로덕션 로직을 테스트에서 다시 구현하지 않기**: 테스트는 독립적인 검증자여야 합니다.

### 실무 모범 사례

- **Mock은 경계에만 사용**: DB, 외부 API, 메시지 큐, 시간 같은 외부 경계만 mock/stub하고 내부 협력은 너무 mock하지 않기.
- **공용 fixture 남용 금지**: 거대한 beforeEach보다 작은 factory/builder가 유지보수에 좋습니다.
- **실제 같은 데이터, 최소한의 데이터**: 운영에서 나올 법한 값은 쓰되, 불필요하게 복잡한 샘플은 피하기.
- **에러 케이스를 1급 시민으로 다루기**: 실패 경로, timeout, 권한 문제, null/empty, retry 등을 꼭 테스트.
- **플레이키 테스트는 즉시 수정/격리**: “가끔 실패”는 방치하면 CI 신뢰가 무너집니다.
- **테스트도 리팩터링 대상**: 중복 제거는 하되, 추상화가 과해서 읽기 어려워지면 오히려 해롭습니다.

### 피해야 할 것

- sleep에 의존하는 테스트
- 현재 시각/랜덤값을 직접 쓰는 테스트
- 내부 구현 디테일에 과하게 묶인 mock-heavy 테스트
- 의미 없이 큰 snapshot
- 테스트 순서에 따라 결과가 달라지는 구조
- 소스 코드나 비즈니스 로직이 테스트 구조에 의존하는 것

### 있으면 좋은 것

- 새 기능은 “정상/경계/실패” 3종 세트
- CI에서 병렬 실행 가능하게 유지

### 한 줄로 요약하면

**작고, 빠르고, 결정적이고, 사용자 관점의 행동을 검증하는 테스트가 프로덕션 모범 사례**예요.
